# SapaRate — оценка качества диалогов операторов

> *Сапа* (каз.) — качество. SapaRate оценивает работу оператора в чате или звонке по чек-листу и показывает, на какие реплики опирается каждая оценка.

Кейс Freedom Broker «Conversation Quality Analytics» (DATA CHALLENGE'26). Команда **PRO и Bali**.

## Что делает система
1. Загружает диалоги (чаты и звонки, RU / KZ / EN) из API организаторов по `group_id` или из JSON-файла.
2. Оценивает каждый диалог по 8 критериям чек-листа: ответ «Да / Нет / N/A» или ступень шкалы, короткое объяснение и номера реплик-доказательств.
3. Считает итог 0–100 (баллы считает код, не модель) и отдельно отмечает грубую ошибку.
4. Показывает всё в интерфейсе: список диалогов, сводка по набору, карточка диалога с переходом к реплике (и к месту в записи звонка), апелляции с решением проверяющего, редактор чек-листа с версиями, сравнение версий.
5. Выгружает результаты в `results/<dev|prod>/results.json` в формате организаторов и проверяет файл.

## Как запустить
Нужен Python 3.10+.
```bash
pip install -r requirements.txt
cp .env.example .env        # Windows: copy .env.example .env, затем впишите свои ключи
python run.py               # открыть http://127.0.0.1:8000
```
В интерфейсе: «Диалоги» → ввести `group_id` → «Загрузить из API» → «Оценить неоценённые». Без ключей система работает в MOCK-режиме (оценки-заглушки, в выгрузку они не попадают).

Тесты: `python -m pytest -q`.

## Какая модель и почему
- **Внешний API Gemini** (режим `external_api`). Причина: бесплатно, быстро (2–5 секунд на диалог), хорошо понимает русский и казахский и возвращает строгий JSON. Локальную модель на ноутбуке не брали: она медленнее и хуже на казахском.
- Бесплатный ключ даёт мало запросов в день (≈20 на модель на аккаунт), поэтому есть **цепочка запасных моделей и ключей**: `gemini-3-flash-preview` → `gemini-3.5-flash-lite` → `gemini-3.1-flash-lite` → `gemini-2.5-flash-lite`. Ключи берутся списком `GEMINI_API_KEYS`. При дневном лимите система сначала переходит на следующий ключ с той же моделью, и только когда лимит кончился у всех ключей — на следующую модель. Лимит «в минуту» не ждётся, ключ меняется сразу.
- Какая именно модель оценила диалог, записывается в оценку и перечисляется в `model.name` файла результатов.
- Запасной провайдер: любой OpenAI-совместимый API (`OPENAI_API_KEY`, по умолчанию Groq).

## Как устроена оценка
- **Один запрос на диалог**: промпт строится из ТЕКУЩЕЙ версии чек-листа (чек-лист не зашит в код) и содержит транскрипт с номерами реплик и «факты», которые считает код (кто писал первым, длинные ожидания).
- Модель отвечает только: ответ по каждому из 8 критериев, объяснение, номера реплик.
- **Код проверяет ответ**: все критерии на месте, значение допустимо (ступень входит в шкалу, N/A разрешён), номера реплик существуют. Если не так — модель получает список ошибок и отвечает ещё раз (в среднем 1,004 вызова на диалог). Если и это не помогло — диалог получает статус `error`, а не выдуманную оценку.
- **Баллы считает `backend/scoring.py`**: «Да» = полный вес, «Нет» = 0, шкала = ступень / максимум; вес критериев с N/A пропорционально перераспределяется на остальные; итог округляется до 2 знаков.
- Доказательства в интерфейсе берутся из транскрипта, а не из текста модели — цитата всегда настоящая.

### N/A и грубая ошибка
- N/A ставится только там, где он разрешён чек-листом и выполнено условие неприменимости; объяснение начинается с этого условия.
- **Грубая ошибка не обнуляет итог**: она отмечается красным флагом отдельно (`critical_flag`). Баллы остальных критериев не меняются.

### Наши трактовки чек-листа (решения команды, записаны в промпте)
- **Завершение**: «Да» только если оператор (подвёл итог ИЛИ предложил дальнейшую помощь) И попрощался. Одно прощание («Хорошего дня») = «Нет». Если чат оборвался до возможности завершить — N/A.
- **Идентификация**: если клиент спросил про свой счёт, но данные ему не раскрыли и защищённого действия не было — N/A. Данные счёта раскрыты до проверки личности — «Нет» (и это может быть грубой ошибкой). Подтверждение личности системой до раскрытия — «Да».
- **Выявление потребности**: если клиент сразу дал все детали (в том числе боту до перевода на оператора), а оператор ответил без уточнений — N/A. Переспрос уже известного — «Нет».
- **Консультация**: ответил ли оператор на вопросы клиента, нет ли ошибочной информации (например, совет «подтверждение личности не нужно»), объяснил ли нужные действия.
- Не оцениваются: порог первой реакции 3 минуты, теги, вложения.

### Звонки
Звонок — автоматическая расшифровка речи, в ней бывают ошибки распознавания и скрытые данные вида `[Имя скрыто]`. Мы не наказываем оператора за ошибки распознавания, «Меня зовут [Имя скрыто]» считается представлением. Время в звонках — ISO 8601: из него считаются секунды от начала; паузы записи («запись приостановлена/возобновлена») вычитаются, чтобы клик по доказательству перематывал плеер на верное место. Ссылка на запись живёт около часа, поэтому сервер достаёт свежую при открытии звонка.

## Выгрузка результатов
```bash
python scripts/export_results.py DEV dev                 # -> results/dev/results.json
python scripts/export_results.py <group_id> prod         # -> results/prod/results.json
python scripts/validate_results.py results/prod/results.json --expect-count 10
```
Формат JSON 1.0: 8 критериев с кодами `contact … critical`, `value` (true/false/число/null для N/A), `rationale`, `evidence_turns` (номера реплик **с 1**; в интерфейсе они с 0 — сдвиг делается при выгрузке), итог и `critical_flag`. Диалог, который не удалось оценить, пишется как `status: "error"` без оценки. Проверка ловит пропуски, дубли, недопустимые значения и неверные номера реплик.

Контрольный час одной командой: `python scripts/control_run.py <group_id>` — скачивает набор, оценивает параллельно, повторяет упавшие, выгружает и проверяет. Подробнее: `docs/control_hour.md`. Проверка без вызовов модели: `--dry-run`.

## Замена критерия
«Чек-лист» → правка текста критерия → «Сохранить как vN» (старые версии и их оценки остаются) → «Диалоги» → отметить галочками нужные диалоги → выбрать новую версию → «Переоценить выбранные» → «Сравнение версий»: таблица по диалогам с итогом до/после и изменившимися критериями. Код критерия (c01…c08) остаётся прежним, поэтому выгрузка работает. Шаги: `docs/criterion_change.md`.

## Апелляции
«Оспорить» критерий → комментарий → «Апелляции»: проверяющий видит спорную оценку и фрагмент диалога, подтверждает или меняет оценку с причиной; итог пересчитывается тем же кодом. Исходный ответ модели не перезаписывается.

## Ограничения (честно)
- **Эталона нет**: точность проверяли только своей ручной разметкой на 15 диалогах DEV (совпадение 86–91% в зависимости от модели). Это не оценка организаторов.
- Самое слабое место — «Корректная консультация» и «Ведение диалога»: модели ставят баллы мягче человека. Лёгкая модель (`flash-lite`) может пропустить грубую ошибку (в DEV — раскрытие данных в `p1-kz-015`); `gemini-3-flash-preview` её находит.
- Бесплатная квота мала; результаты DEV собраны одной лёгкой моделью, а на контрольном наборе используется лучшая из доступных. Ответ модели не строго детерминирован: два запуска могут отличаться на ступень шкалы.
- «Установление контакта» не поддерживает N/A (для звонков, где приветствие не попало в запись, формат организаторов допускает `null`) — такого значения система не выдаёт.
- Если добавить девятый критерий, он войдёт в оценку и итог в интерфейсе, но в `results.json` его нет: формат принимает ровно 8 кодов.
- Модель видит только текст транскрипта: интонацию, паузы в речи и качество звука она не оценивает.
