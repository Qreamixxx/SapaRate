## Что это и зачем
SapaRate читает диалоги операторов с клиентами (чаты и звонки на русском, казахском и английском) и оценивает работу оператора по чек-листу из 8 критериев. Для каждой оценки видно короткое объяснение и реплики, на которые модель опирается, поэтому результат можно проверить глазами.
Баллы и итог считает программа по понятной формуле, а не модель. Если оценка спорная, её можно оспорить, а проверяющий подтверждает или меняет её с причиной.

## Как запустить
Нужен Python 3.10+.
```bash
pip install -r requirements.txt
cp .env.example .env        # Windows: copy .env.example .env, затем впишите свои ключи
python run.py               # открыть http://127.0.0.1:8000
```
В интерфейсе: «Диалоги» → «Загрузка и оценка» → ввести `group_id` → «Загрузить из API» → «Оценить неоценённые». Без ключей система работает в MOCK-режиме (оценки-заглушки, в выгрузку они не попадают).
Тесты: `python -m pytest -q`.

## Что умеет система
- Загружает диалоги из API организаторов по `group_id` или из JSON-файла.
- Оценивает по 8 критериям: «Да / Нет / N/A» или ступень шкалы, объяснение, номера реплик.
- Считает итог 0–100 и отдельно отмечает грубую ошибку.
- Список диалогов с поиском, сводка по набору, карточка диалога с переходом к реплике (и к месту в записи звонка).
- Апелляции: оспорить критерий, решение проверяющего, пересчёт итога.
- Редактор чек-листа с версиями, переоценка выбранных диалогов, сравнение версий.
- Веса в редакторе: режим «Сумма всегда 100» (по умолчанию: изменённый вес закрепляется замком, остальные пересчитываются пропорционально) и «Свободный» (любая сумма, кнопка «Привести к 100»). Дробные веса поддерживаются.
- Светлая и тёмная тема (переключатель в шапке, выбор запоминается).
- Окошко у значка «модель» в шапке: цепочка провайдеров и моделей, статус.
- Подтверждение перед большими запусками: если оценка потребует больше 3 запросов к модели, система спрашивает «Будет N запросов. Продолжить?».
- Выгрузка в `results/<dev|prod>/results.json` и проверка файла.

## Какая модель и почему
- **Внешний API Gemini** (режим `external_api`): бесплатно, 2–5 секунд на диалог, хорошо понимает русский и казахский, возвращает строгий JSON.
- Бесплатная квота мала (около 20 запросов в день на модель на аккаунт), поэтому есть цепочка: `gemini-3-flash-preview` → `gemini-3.5-flash-lite` → `gemini-3.1-flash-lite` → `gemini-2.5-flash-lite`, и несколько ключей (`GEMINI_API_KEYS`).
- При дневном лимите система сначала берёт следующий ключ с той же моделью, и только когда лимит кончился у всех ключей, — следующую модель. Лимит «в минуту» не ждётся.
- **Запасной провайдер Groq** (`openai/gpt-oss-120b`) стоит последним: он включается, только когда у всех Gemini-ключей и моделей лимит. Его точность по нашей проверке ниже, чем у Gemini.
- Имя модели, которая оценила диалог, записывается в оценку и перечисляется в `model.name` файла результатов.

## Как устроена оценка
- Один запрос на диалог. Промпт собирается из ТЕКУЩЕЙ версии чек-листа (чек-лист не зашит в код) и содержит транскрипт с номерами реплик и «факты», которые считает код.
- Модель отвечает только: ответ по каждому критерию, объяснение, номера реплик.
- Код проверяет ответ: все критерии на месте, значение допустимо, номера реплик существуют. Если нет — модель получает список ошибок и отвечает ещё раз (в среднем 1,004 вызова на диалог). Если не вышло — статус `error`, без выдуманной оценки.
- Баллы считает `backend/scoring.py`: «Да» = полный вес, «Нет» = 0, шкала = ступень / максимум. Вес критериев с N/A пропорционально делится между остальными. Итог — доля набранного от максимума применимых критериев × 100, округление до 2 знаков.
- Поэтому итог не превысит 100, даже если сумма весов в редакторе стала 101.
- Доказательства в интерфейсе берутся из транскрипта, а не из текста модели: цитата всегда настоящая.

### N/A и грубая ошибка
- N/A ставится только там, где он разрешён чек-листом и выполнено условие неприменимости.
- Грубая ошибка не обнуляет итог: она отмечается красным флагом отдельно (`critical_flag`).

### Наши трактовки чек-листа (записаны в промпте)
- **Завершение:** «Да» только если оператор (подвёл итог ИЛИ предложил дальнейшую помощь) И попрощался. Одно прощание = «Нет». Если чат оборвался до возможности завершить — N/A.
- **Идентификация:** клиент спросил про свой счёт, данные не раскрыли, защищённого действия не было — N/A. Данные раскрыты до проверки личности — «Нет» (возможна грубая ошибка).
- **Выявление потребности:** клиент сразу дал все детали (в том числе боту), оператор ответил без уточнений — N/A. Переспрос известного — «Нет».
- **Консультация:** ответил ли оператор на вопросы, нет ли ошибочной информации, объяснил ли нужные действия.
- Не оцениваются: порог первой реакции 3 минуты, теги, вложения.

### Звонки
- Звонок — автоматическая расшифровка речи: бывают ошибки распознавания и скрытые данные вида `[Имя скрыто]`. Оператора за ошибки распознавания не наказываем.
- Время в звонках — ISO 8601, из него считаются секунды от начала. Паузы записи вычитаются, чтобы клик по доказательству перематывал плеер в верное место.
- Ссылка на запись живёт около часа, сервер достаёт свежую при открытии звонка.

## Выгрузка результатов
```bash
python scripts/export_results.py DEV dev                 # -> results/dev/results.json
python scripts/export_results.py <group_id> prod         # -> results/prod/results.json
python scripts/validate_results.py results/prod/results.json --expect-count 10
```
- Формат JSON 1.0: 8 критериев (`contact … critical`), `value` (true/false/число/null для N/A), `rationale`, `evidence_turns`, итог и `critical_flag`.
- Номера реплик считаются **с 1** и в интерфейсе, и в `results.json`, они совпадают.
- Диалог, который не удалось оценить, пишется как `status: "error"`.
- Проверка ловит пропуски, дубли, недопустимые значения и неверные номера реплик.

Контрольный час одной командой: `python scripts/control_run.py <group_id>`: скачивает набор, оценивает параллельно, повторяет упавшие, выгружает и проверяет. Подробнее — `docs/control_hour.md`. Проверка без вызовов модели: `--dry-run`.

## Замена критерия
1. «Чек-лист» → правка текста критерия → «Сохранить как vN» (старые версии и оценки остаются).
2. «Диалоги» → отметить галочками диалоги → выбрать новую версию → «Переоценить выбранные».
3. «Сравнение версий»: итог до/после и изменившиеся критерии по диалогам.

Код критерия (c01…c08) не меняется, поэтому выгрузка работает. Подробнее — `docs/criterion_change.md`.

## Апелляции
«Оспорить» критерий → комментарий → «Апелляции»: проверяющий видит спорную оценку и фрагмент диалога, подтверждает или меняет оценку с причиной; итог пересчитывается тем же кодом. Исходный ответ модели не перезаписывается.

## Ограничения
- Эталона у нас нет. Точность проверяли на 15 диалогах DEV по своей разметке, сделанной с помощью ИИ (не экспертами): совпадение по критериям 86–91% у Gemini, 76% у Groq.
- Слабее всего «Консультация» и «Ведение диалога»: оценка по шкале иногда на ступень выше, чем в нашей разметке.
- Два запуска модели могут отличаться на одну ступень шкалы.
- Если у лучшей модели кончилась квота, система переходит на более лёгкую. Какая модель оценила диалог, видно в карточке и в results.json.
